O *Product Backlog* é o coração de qualquer produto ágil. Se ele for apenas uma "lista de desejos" mal escrita, a equipe de engenharia construirá a funcionalidade errada e o dinheiro da empresa irá para o ralo.

Product Owners (POs) de elite não perdem tempo reinventando a roda. Eles utilizam estruturas validadas (frameworks) para descrever o trabalho com clareza matemática. Abaixo, disponibilizamos a estrutura exata que você deve usar nas suas ferramentas (Jira, Trello ou Azure DevOps).

## A Estrutura em 3 Níveis

Para organizar centenas de demandas, você precisa quebrar o trabalho em hierarquia:

1.  **ÉPICO (A Grande Visão):** Uma iniciativa estratégica que leva semanas ou meses.
2.  **HISTÓRIA DE USUÁRIO (O Valor):** O pedaço do Épico que pode ser entregue em 1 Sprint.
3.  **SUBTAREFAS (A Execução Técnica):** Como os desenvolvedores vão fazer o código acontecer.

## Exemplo Prático de Preenchimento

Imagine que o nosso Épico seja: **"Criar um sistema de Login e Autenticação de Usuários"**.

### A História de Usuário (User Story)
A regra de ouro é usar o formato: `Como um [Perfil], eu quero [Ação] para que [Benefício/Valor]`.

*   **Título do Card:** Login via Google (SSO)
*   **Descrição:** *Como um* usuário novo do aplicativo, *eu quero* poder me cadastrar usando minha conta do Google, *para que* eu não precise criar e memorizar uma nova senha, acessando o sistema em segundos.

### Os Critérios de Aceite (BDD Format)
A História explica a dor, mas são os *Critérios de Aceite* que definem quando o cartão pode ser arrastado para a coluna de "Concluído" (*Definition of Done*). Use a estrutura `Dado que / Quando / Então`.

*   **Cenário 1: Login com Sucesso (Caminho Feliz)**
    *   **Dado que** o usuário está na tela inicial de login;
    *   **Quando** ele clica no botão "Entrar com o Google" e aprova a permissão no pop-up;
    *   **Então** o sistema deve redirecioná-lo para o Painel de Controle e exibir a mensagem "Bem-vindo".

*   **Cenário 2: Tratamento de Erro**
    *   **Dado que** o usuário está tentando fazer o login;
    *   **Quando** a API do Google estiver indisponível ou a internet cair;
    *   **Então** o sistema não deve travar, mas sim exibir o alerta vermelho: "Serviço indisponível no momento. Tente usar e-mail e senha".

## O Segredo da Priorização (DEEP)

Para garantir que o seu template de Backlog seja funcional, ele deve seguir a sigla **DEEP**:
*   **D**etalhado apropriadamente (itens do topo bem explicados, itens do fundo vagos).
*   **E**stimado (com Story Points, pelo menos os itens do topo).
*   **E**mergente (ele muda todos os dias conforme o mercado muda).
*   **P**riorizado (o que dá mais lucro ou resolve mais riscos fica em cima).
